OKX and Gate single-order lookups are adapter-level fixtures without a remotely callable Admin route. An absent order remains unresolved. Gate documents that after 60 seconds a cancelled, unfilled order can disappear from custom-ID lookup, and the exchange-ID lookup also has retention limits. Preserve the original client and exchange IDs whenever available.

OKX single-order cancellation is `MOCK_READY` with synthetic credentials and explicit fixture transport. The adapter validates the original open order, submits a single cancellation, checks the acknowledgment, and retrieves terminal order status. Cancellation leaves prior fills intact, so the fixture does not imply a flat position. Uncertain cancellation requires reconciliation, and the Admin lifecycle remains `EXECUTION_BLOCKED`. [OKX order API](https://www.okx.com/docs-v5/en/#order-book-trading-trade-post-cancel-order)

## Remote readiness and approval

All providers are **REMOTE_BLOCKED** for this work. Before credential setup, independently confirm the applicable regional entity, operator and egress eligibility, product permissions, and intended data use. Verify the isolated Staging schema, approved server-side encryption, actor-scoped privileged access, and redacted audit trail. Obtain a distinct approval for each provider's credential write through the approved encrypted path.

Separately approve a finite signed read for the named provider, environment and account. Use the minimum approved API permissions. A successful public request does not establish Demo credential provenance. Validate ownership and environment using provider-supported account evidence and stop on mismatch or denial. On shared hosts, require the documented simulation header in addition to Demo key provenance. Keep signed requests on fixed reviewed targets and reject redirects.

An individual Demo order requires separate approval that identifies the provider, credential scope, contract, order mode, size, price, TP/SL, expiry, idempotency key and reconciliation ownership. Before requesting that approval, verify exact contract precision and units, provider response reconciliation, venue-native stop and close behavior, and liquidation/margin risk in that account mode. Unknown or ambiguous submissions require status reconciliation before any further submission. No provider-specific execution guarantee follows from the presence of an API method in documentation.
