# Public market worker to website: inactive downstream foundation

The local worker currently writes observation segments and health metadata to its own persistent disk. The deployed website reads existing `scanner_candidate_snapshots` and reports the continuous worker inactive. Starting the worker does **not** connect those two systems. This preparation does not change that boundary.

## Implemented offline

`lib/intelligence/public-market-projection.ts` adds `PublicMarketProjection`, a pure bounded read model without database/network imports, pool creation, API route wiring or activation. It stores at most one latest validated observation for each explicitly selected symbol (maximum 200, within a bounded discovered universe). Known fields, finite numeric values, quote-flow consistency, fresh/sequence flags, valid timestamps and required nonnegative epochs are checked. Invalid or stale input cannot replace a valid row. Duplicates are deterministic, identity conflicts reject, and older per-symbol epochs/timestamps cannot rewind state.

Checkpoint restore validates the bounded state and preserves original timestamps. Viewing a restored checkpoint recomputes sample age; old samples return STALE with no price. It never labels replayed history as live data. `batchPlan(expectedRevision)` produces a deterministic `DRY_RUN_ONLY` proposal containing expected/next revision and snapshot; it has no executor and explicitly sets remoteWriteAuthorized false.

The website-shaped view separates selected observation recency from universe size. Rows are labelled RECENT_OBSERVATION, never FRESH: the shared observation eventTime is the newest participating input, so it cannot prove that the oldest trade/book/ticker input remains within its freshness deadline after receipt. Each row explicitly reports freshnessVerified false and requiredInputFreshness UNKNOWN_AFTER_RECEIPT. A recent sample price is not certified current/live. Selected observations do not prove all-universe ticker delivery; tickerCoverage remains NOT_PROJECTED. continuousFeedVerified and executionEnabled remain false, and candidates remain empty. The new module is not imported by current website readers. Its view is an integration target, not a claim that existing scanner database columns can accept these records directly.

Six tests cover an actual warmed `BinanceMarketFeed` fixture flowing into the projection, duplicate/conflict handling, old/new epochs, unknown/credential-bearing fields, timestamps, stale restart checkpoints, coverage bounds and deterministic dry-run plans. Tests use local fixtures only. No SQL, network connections or remote writes are involved.

## Missing implementation before website activation

1. **Durable source envelope and acknowledged tailer.** Observation files currently have no globally durable logical event sequence/cursor. A future reader must identify run epoch, segment and committed byte offset, validate complete bounded NDJSON rows and checkpoint the exact source cursor. Journal ring rotation can delete unread history; detect and report such a gap rather than silently resetting it. The projection's per-symbol duplicate detection is not a replacement for a transactional source acknowledgement. Do not assume exactly-once delivery.
2. **Dedicated credential-free ingestion boundary.** Keep database credentials off the public WebSocket worker. A separately reviewed server-side importer can read approved artifacts/transport and enforce source identity, schema, rate, freshness, payload size and explicit Staging target. It must not share application order, credential or notification access. Transport provisioning and authentication are separate approvals; no endpoint/token is created here.
3. **Transactional storage adapter and approved schema.** Review a private public-data snapshot/heartbeat store and least-privilege writer role after the backup/restore gate. In one transaction, compare the last revision/source cursor, apply the snapshot and commit the cursor acknowledgement. Reconcile lost COMMIT responses using the same batch identity. This module only proposes that transaction; it neither implements persistence nor modifies the existing scanner schema. Do not add a privileged writer to the worker to avoid this step.
4. **Read-only website repository.** After approved storage exists, add a server repository/API reader that checks Staging isolation, per-symbol input ages, source epoch, completeness and current worker heartbeat. The future producer contract must carry oldest-required-input timestamps or an independently derived expiry; the current newest-input eventTime is insufficient for downstream freshness certification. Expired/missing/disconnected evidence must remove readiness. Keep previous saved scanner coverage separate, rather than treating a recent maximum timestamp as proof every symbol is fresh. Review cache TTL/polling and stale UI handling. No current route is changed by this release.
5. **Research prerequisites.** Fresh quotes alone cannot create strategy candidates. Closed bars with availability timestamps, strategy/research processing and durable decision evidence are still needed. Open-interest enrichment is optional and presently absent. No momentum, whale attribution, Standard/High-Risk readiness or paper execution is inferred from projected prices.
6. **Operational evidence.** Validate actual transport loss/restarts, retention gaps, transactional retries, schema/grants and website freshness end-to-end using authorized disposable Staging fixtures. Local projection tests and a future worker-only soak do not prove those boundaries.

## Separate approvals

The proposed 20-symbol local-journal soak needs host/region/spend/network/retention/service-start approval. It can run without database credentials and without website refresh. Website ingestion needs a separate reviewed source transport, backup/restore evidence, exact schema/grant approval and explicit permission for bounded public-data Staging writes. Reader activation follows a successful transactional integration test. None of those approvals includes migrations, notifications, CRON, paper execution, exchange orders, credential enablement or Production deployment.
